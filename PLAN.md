## Checkpoints: when to stop and plan (agreed 2026-10-13)
Within a written step, work goes ahead without asking. **Stop, report plainly (where we are, what the numbers say, what next) and agree the next steps with the author** at any of these checkpoints:
1. **A milestone's done-when is reached**: the author confirms it before the next milestone starts.
2. **A decision gate resolves** (pre-registered test or pre-written rule) and the result changes the route.
3. **New data is needed**: a recording or live test only the author can do at the camera.
4. **The written plan runs out**, or the next step needs a design choice the plan does not make (then propose the steps, with a recommendation).
5. **Before anything hard to undo or outward-facing**: pushing to `main`, deleting branches or data, sending data off the machine.
Between checkpoints: commit as work goes, keep the private progress notes current (and write every new pre-registration into PREREGISTRATIONS.md, committed before its data), and do not build ahead of the current step.

**Order (agreed 2026-10-14):** L1 = M3 step 6c (now) -> L2 (before M3 step 7) -> M3 step 7 -> M3 step 8 with L5 -> L4 and L3 (M4) -> L6 (M5). L1 and L2 come before M3 step 7; L3, L4 and L6 do not block M3.

Goal: every session makes the tracker better, for the author now and for other people later (see CLAUDE.md "Learning loop and data strategy"). Steps (order above; each claim pre-registered when its step starts):
- **L1. Data contract:** structured condition tags + person id on every session and Cursor log (done together with the condition tags as M3 step 6c, decided at checkpoint 4; its done-when is there). Schema check: `session_report.py` check 6 already warns on missing tags for calibrations; it refused `cursor_*` logs and Cursor-mode calibrations (because round 4 was frozen without the report); done in 6c stage 2: they get a tag-only check that reads `meta` only, round-4 classification untouched. Align the check-6 tag set with the CLAUDE.md data contract (lighting, screen layout).
- **L2. Keep and version learned state:** raw clicks are already kept in `cursor_*.npz`, but the learned model state lives in one overwritten `last_calibration.npz` (`resume.py`) so it is not versioned and is replaced at the next save after the 12 h limit, `--fresh` or Cmd+Option+R (it may be rebuildable offline from the click logs, as `evaluate_online.py` replays them); keep every model state with its provenance; the live model may still start fresh, but history is never lost.
- **L3. Long-term personal model:** train on all of the author's calibrations and Cursor clicks across days; each session starts from it and adapts (session level). Pre-registered test vs today's 12 h reuse + click learning, paired on the same clicks. Training pool = sessions before a frozen cutoff (round-3 set-B and round-4 test sessions may be training data, never L3 test data); test = new qualifying sessions after the freeze, never fed into the personal model before their own evaluation (no rolling update during the test); primary CI two-level (sessions, then clicks), as round 4 showed the click-level CI is optimistic. Leave-one-session-out over the old pool is exploratory, for model choice only.
- **L4. Real-use monitoring:** a daily gaze-to-click error summary from Cursor logs, with drift flags. A monitoring signal, never evidence for a claim. Biased labels: clicks without looking, predictions from a model that learned from earlier clicks, the warp shaping where clicks land; so use predict-then-update predictions only, a fixed gate on a frozen reference model's prediction, mean / median / p90 per day, and drift thresholds written down before first use.
- **L5. Population prior:** join with M3 step 8 (pretrained gaze model) as the population level; personal model = correction on top.
- **L6. Multi-person (with M5):** consent flow, on-device storage, opt-in sharing of anonymous features and labels or federated updates; leave-one-person-out evaluation and per-group results (the person is the unit, so CIs stay wide with few people; check a pretrained model's training data does not include the evaluated person).

## M5 (later): Generalise beyond this MacBook

Goal: **works with any webcam and any screen layout after a ~30-second calibration, and stays accurate as you move.** Zero-calibration for anyone is research-grade and out of scope.

- **Architecture:** separate person -> 3D gaze ray, camera geometry (intrinsics + pose), screen geometry (one plane per display, from macOS display arrangement + a few calibration dots per screen). New setup = locate camera/screens, not relearn the eyes.
- **5a. Your own variations (cheapest real test):** external webcam (on top of a monitor), second/extended monitor, different desk distances and chair heights.
- **5b. Other people:** friends/family with consent; public datasets for pretraining or evaluation (MPIIFaceGaze, GazeCapture, ETH-XGaze, Gaze360; mostly non-commercial research licences, so check before any product use). Few-shot personal calibration on top of a general model (domain adaptation).
- **5c. Other OSes:** Windows / Linux sinks for cursor control and screen geometry; core unchanged.
- **Active calibration (from M2 step 7, stretch):** pick the next calibration point where the model is least certain, so a new setup needs fewer dots.
- **Data design** (continues M2 step 4; cross-session error stays the headline; H6 showed one long session can carry a result, so the matrix must balance sessions per condition): planned (fractional) condition matrix over camera x screen x lighting x glasses x posture rather than ad-hoc recording; every session tagged.
- **Evaluation:** leave-one-condition-out, leave-one-person-out, and per-group results (glasses, face types, lighting) as a fairness check; an accessibility tool that works worse for some faces is a real problem.

**Done when:** on held-out setups and held-out people, a short calibration reaches accuracy close to the single-setup result, with per-condition and per-group numbers reported.
