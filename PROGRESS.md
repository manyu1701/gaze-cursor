## Pre-registration: M2 hypothesis H1 (written 2026-10-13, BEFORE recording any layout-v2 session)
- **H1:** with pose-free features, `gaze_blend` (iris xy + the 14 eye blendshapes = 18 features) with ridge alpha=100 has lower cross-session error than `gaze` (iris xy, 4 features) with ridge alpha=10.
- **Data:** three new sessions recorded with calibration layout `v2` (25 targets), at different times of day/lighting, each tagged with `--note`. **Inclusion rule, fixed now:** `meta.layout == "v2"` and window `[0,0,1470,956]`. No session is dropped after seeing results; a session is dropped only for an objective failure (< 80% valid frames, or the target-safety abort), logged with the reason.
- **Primary (confirmatory) analysis:** leave-one-session-out. For each v2 session, train on the pooled targets (calibration and held-out) of every *other* clean session (the older clean sessions plus the other v2 sessions) and test on **all 25 targets of the held-out session**. Unit of analysis = target. Per-target error = mean over frames of Euclidean error in degrees of visual angle. Both configs are evaluated on identical targets (paired).
- **Primary statistic:** mean of the per-target paired differences d = err(`gaze` a=10) - err(`gaze_blend` a=100) (positive favors H1), with a 95% bootstrap CI resampling targets (10,000 resamples, fixed seed).
- **Success criterion (all three required):** (a) the CI lower bound is > 0; (b) the mean improvement is >= 0.25 deg; (c) `gaze_blend` is better in at least 2 of the 3 held-out sessions. Otherwise H1 is reported as **not supported**, with no re-tuning on these sessions.
- **Caveats, stated up front:**
  - The three clean M1 sessions (including Independent analysis #2) suggested the hypothesis, and alpha=100 was also suggested by them; they are exploratory and never confirmatory.
  - The comparison changes features and alpha together, so a win does not say which caused it. Secondary diagnostic configs (reported, not part of the criterion): `gaze` alpha=100 and `gaze_blend` alpha=10.
  - Three sessions carry little session-level information. A secondary sensitivity analysis uses a two-level bootstrap (resample sessions, then targets).
  - Everything else computed is exploratory and labeled so (`confirmatory=0` in `results.csv`).

## M2 step 3 implementation notes (2026-10-13, before any model was fitted to set A)
- **Head geometry** (`features.head_geometry`, appended to the base features as `head_x`, `head_y`, `head_z`; `N_FEATURES` 9 -> 12, the old feature sets still use the first 9, so earlier results are unchanged): eye centres = midpoints of the eye corners (the irises move with gaze, the corners do not); depth from their apparent distance, corrected for head yaw (`/ cos(yaw)`, capped at 60 deg). Pinhole model with the principal point at the image centre: `head_x`, `head_y` in cm (no focal length needed), `head_z` = depth x (image width / focal length), so no camera value is assumed. `IPD_CM` = 6.3 only rescales and is absorbed by the linear models. Recomputed from stored landmarks, so every old session has it.
- **3a `head`:** iris (4) + head pose (3) + head position (3), ridge. **3b `ray`:** the first-order gaze-ray / screen-plane intersection. The camera is in the screen plane, so a ray from eye (x, y, z) at angles (a, b) hits (x + z tan a, y + z tan b); with gaze angle = head rotation + eye-in-head rotation (linear in the iris offset), the hit point is linear in (x, y, z, z x iris offsets, z x yaw, z x pitch). Ridge learns the per-person eye gain, the unknown focal length and the camera-to-screen offset. The full non-linear version (tan, roll) is a possible next step if set A shows the linearisation matters.
- **Synthetic world test** (`tests/test_prereg3.py`): a simulated camera, eyes at known 3D positions with 0.5 cm sway, and gaze rays to known targets, generated as landmarks and run through the real pipeline. Leave-one-position-out over the six set-A-like positions: `gaze_a10` 1.7-7.8 deg, `head_a10` 0.4-1.9, `ray_a1` about 0.1. It only shows the code does what the geometry says; it is not evidence about real data. Lesson from building it: a factor that never varies in the calibration data (e.g. head height, if only one session moves vertically) cannot be learned; real head sway helps, which is another reason set B should vary positions moderately.
- **Selection:** set A is named in `prereg3.SET_A`. ## M2 step 6 (smoothing): selection rule (written 2026-10-13, BEFORE any filter was tuned)

- **Metrics:** jitter = sqrt(var x + var y) of the filtered output in each fixation from 300 ms after its start, in deg; lag50 / lag90 = time from the step until the filtered output covers 50% / 90% of the jump between the two fixations' raw mean predictions (only jumps >= 3 deg); overshoot past 100%; steady-state error vs the target. Unit = fixation; bootstrap CIs over fixations.
- **Rule:** among the grid (raw; moving average n 3/5/9; One-Euro min_cutoff {0.05, 0.1, 0.3, 1, 3} Hz x beta {0, 1e-3, 3e-3, 1e-2, 3e-2} per px/s, d_cutoff 1 Hz; snap-on-saccade variants of the 3 best), choose the config with the **lowest development jitter subject to median lag50 <= 100 ms and median lag90 <= 250 ms**. ## Head-transform check: decision rule (written 2026-10-13 evening, BEFORE computing anything; next step 1)
- **Question:** does the translation of MediaPipe's facial transformation matrix (`transform[:3, 3]`, canonical-face units ~cm) track the real head moves, where the eye-corner estimate (`head_x/y`) did not (set A free fit -4..-9 vs +-50.6 points/cm)?
- **Data:** set B only (laptop and lid fixed, only the head moved): C, N, R, L, Rt, Lo, C2, all frames with valid features. Set A reported alongside (laptop may have moved), not part of the rule. Exploratory diagnostic, `confirmatory=0`; no model is chosen from it.
- **Axes (fixed before looking at gaze):** map the transform translation to the image convention of `head_x/y` (x image-right, y image-down) by the sign of its frame-wise correlation with `head_x` / `head_y` on set B (an axis convention check, not an outcome). If |r| < 0.5 on either axis, report that as a failure of the transform to track position at all.
- **Primary statistic:** the same free least-squares fit as `diagnose_positions.py`: screen x, y (points) ~ 1 + iris (4) + yaw + pitch + head x + head y, over all set-B frames, once with the eye-corner `head_x/y` and once with the transform's (tx, ty) in cm. Ratio = fitted head coefficient / geometric prediction (x: -1/cm_per_px, y: +1/cm_per_px; ~50.6 points/cm on this screen).
- **Decision:** the transform **tracks head moves** if both its x and y ratios lie in **[0.5, 2.0]** (right sign, within a factor of 2). Then the geometric gaze-ray route is un-parked: the next step is a pre-registered geo model using the transform translation, tested on NEW position sessions (set B is used up). Otherwise it stays parked and automatic head adjustment goes via M3's click-based self-recalibration (and later a pose-invariant pretrained model, M2 step 8). If the eye-corner estimate ALSO lands in [0.5, 2.0] on set B, set A's failure is attributed to the laptop moving, and the simpler eye-corner estimate is preferred.
- **Reported, not part of the rule:** per-session median translation vs C (cm) next to the nominal moves (sideways ~10 cm, Lo ~8 cm lower, N/R distance x1.28 / x0.86 by eye spacing); depth ratio tz(N)/tz(C), tz(R)/tz(C) vs those ratios; the same fits on set A.
- **Caveat:** in the free fit, the iris features partly absorb head movement (turning the head to face the screen changes them), so a ratio below 1 is expected even for a perfect head estimate; the 0.5 lower bound allows for this. The nominal moves are rough (no tape measure).

**RESULT (run once, 2026-10-13 evening, `scripts/diagnose_head_transform.py`; logged as `head_transform_check`, confirmatory=0):**
- Set B, 5299 frames. Axis check PASS (r = +1.00 / -1.00). **Ratios to geometry: transform x +0.25, y +0.17; eye corners x +0.25, y +0.18** (rms residual 192 pt for both). Both below 0.5: **by the rule, the geometric route stays parked; automatic head adjustment goes via M3 click-based self-recalibration** (and later a pretrained gaze model, M2 step 8).
- Set A (reported): transform x +0.08, y -0.15; eye corners x +0.08, y -0.14.
- **Exploratory reading (not part of the rule):**
  - The transform translation is **the same signal as the eye-corner estimate** (|r| = 1.00 on both axes, both sets): both come from the same landmarks, so it adds nothing.
  - The head estimate **does** track the physical moves on set B: L +10.1 cm, Rt -9.3 cm (nominal ~10), Lo +6.1 cm lower (nominal ~8), N/R depth ratio 0.80 / 1.14 (transform) vs 0.79 / 1.17 (eye spacing). The set-A diagnosis ("measured head movement 5-10x too large") is therefore revised: the set-A moves were genuinely large (L +17 cm, R/L/Rt/Lo 9-17 cm lower), and **what is ~4-6x too small is how the gaze data respond to head position, not the head estimate.** Likely cause: the iris-in-eye features are not a clean eye-rotation measure (normalised by eye width, off-axis foreshortening, and the head turning to face the screen), so a fixed head-offset term cannot correct them linearly. This matches the live result that off-axis viewing degrades accuracy even after recalibration.
  - Implication: the geometric ray needs a better gaze-direction estimate, not a better head position. That is M2 step 8 (pretrained, pose-invariant gaze model) feeding the already-good head position; until then, recalibration (R / click-based) is the fix.

## Target practice (added 2026-10-13, at Abhimanyu's request: "I can't tell if the dot follows my eye; give me something to aim at")
- `Practice.command` / `scripts/target_practice.py`: a box appears; move the gaze dot into it and hold it (dwell 0.6 s, brief exits < 0.15 s forgiven) until it fills; a miss after 8 s. 2-down/1-up staircase on the box size (x0.8 after two hits, x1.25 after a miss, 15-300 pt half-side), so it settles near the size hit ~71% of the time. Summary: hit rate, median time to hit, reliable box size (median of the last 8 boxes, cm and deg), mean dot-to-centre distance after the first 0.4 s of each box, and the systematic offset (`describe_bias`, reported above 0.5 cm). Uses the latest calibration, or `--pool`.
- Every frame is saved as a labelled session (`kind: target_task`, phase TEST, target = box centre) to `data/tasks/` (gitignored, never selected as a calibration), with the trials and summary in `meta`; one row per run goes to `results.csv` (mode `target_task`). These are candidate data for later online learning (M3: "every click is a label"). ## Display facts (locked in `ScreenConfig`)
- Panel (Apple tech specs, support.apple.com/en-us/126320): 13.6" Liquid Retina, 2560x1664 at 224 ppi (= 29.0 x 18.9 cm; Quartz/EDID gives 29.06 x 18.90). Apple: only the TOP corners are rounded (bottom square) and the actual viewable area is smaller than the 13.6" rectangle.
- Default mode is "looks like 1470x956" (rendered at 2x = 2940x1912, downscaled to the panel), so 1 pt = 0.01975 cm. Pixels everywhere in this project are logical points.
- Measured via AppKit on this Mac (MacBook Air Mac17,3, M5, 16 GB): `safeAreaInsets.top` = 32 pt (menu bar/notch strip); notch spans x = 646..825 pt (179 pt wide, 32 pt tall). `ScreenConfig.from_system()` reads these and the physical size (Quartz). Viewing distance is an assumed 60 cm.
- Corner radius: NOT published by Apple and no public API; `corner_radius_pt = 24` is a generous ASSUMPTION used only to keep targets away. `target_is_safe()` rejects targets within the ring radius of the edges, the 32 pt strip or the rounded corners; `calibrate.py` aborts if any are unsafe. `--check-screen` draws the four extreme-safe rings plus the notch outline.

## Gotchas and decisions
- Pose sign conventions on the UNFLIPPED frame (what recordings use): pitch negative = head tilted back/looking up; yaw and roll signs are inverted relative to the old mirrored viewer. The viewer now processes the raw frame and mirrors for display only (landmarks drawn at 1 - x). The webcam sits low, so neutral pitch reads about -2 to -13. Head pose assumes R = Ry(yaw) Rx(pitch) Rz(roll) with scale removed.
- No component mirrors the frame it processes; sessions record `mirrored: false`.
- Landmarks: 478 points; right iris 468-472 (center 468), left iris 473-477 (center 473); x/y normalized. VIDEO mode needs strictly increasing timestamps (`FaceTracker.process` enforces this).
- Blendshapes (52) are recorded per frame; names are in `meta["blendshape_names"]`. Candidate subset = `BLEND_FEATURE_NAMES` (eyeLook In/Out/Up/Down, Blink, Squint, Wide, L/R = 14). Tracker cost measured live: median 10.1 ms with blendshapes vs 7.2 ms without (p95 12.6 vs 13.4), fine for 30 fps.
- Quartz/Cocoa pyobjc were pulled in at M1 (CLAUDE.md originally said M3) for screen geometry and the overlay window.
- `eval/targets.py` held-out function is `held_out_points` (a `test_` name would be collected by pytest).
- No model save/load yet: Run fits a fresh quick calibration on start (or refits from a session with L / --latest).
- Deps: mediapipe 1.1.0, opencv-python 5.0.0.93 (mediapipe also pulls opencv-contrib-python; harmless), numpy 2.5.4.
- Settle frames (0.7 s per target) are not recorded; M2 step 6 measured filter lag on spliced fixations instead (`eval/temporal.py`), and the live path test measures end-to-end lag.
- Commands run through `!` in Claude Code go through an app without Camera permission: camera scripts must be run from Terminal / the .command launchers (reading saved data works with `!`).
- `Calibrate.command` re-asks on an empty note (a set-B session was once lost that way); the guided flow opens two canvases, so the NSWindow subclass is created once per process.
